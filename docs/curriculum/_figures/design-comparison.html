Ticket

“My blender arrived cracked. I want my money back.”

No order number. The customer has two recent orders.

Shared by every design

  • Refund
  • Escalate
  • Reject

One model, an order-lookup API, and a runtime rule: refunds above $100 or older than 30 days go to a person.

  • Single LLM call

    Next step: none to pick

    1. Model drafts a reply
    2. A person reads the draft and acts. No handler runs. 1 model call.

  • Fixed pipeline

    Next step: code, in a fixed order

    1. Model summarizes
    2. Model labels it “damaged item”
    3. Model drafts a reply
    4. Every ticket gets the same three steps, and a person still acts. 3 model calls.

  • Rules workflow

    Next step: code, by business rules

    1. Model extracts: blender, cracked, no order number
    2. Rule: no order number → Escalate
    3. Run: Escalate
    4. A person takes over. No refund without an order number, but staff time is spent. 1 model call.

  • Learned router

    Next step: the model, once

    1. Model picks a handler: Refund
    2. Refund precondition fails: no order number
    3. Fallback in code — Run: Escalate
    4. A person takes over. The model's one choice, made from the ticket text alone, was spent. 1 model call.

  • Agent

    Next step: the model, after each result

    1. Model chooses: look up the customer’s orders
    2. Result: #1043 blender, $79, 12 days ago · #0988 kettle, $129, 50 days ago
    3. Model proposes: refund #1043
    4. Runtime check: $79, 12 days ✓
    5. Run: Refund #1043
    6. Result: refund receipt for #1043
    7. Model drafts a reply citing the receipt and proposes to stop
    8. Runtime accepts the stop
    9. The lookup result determined the next choice. 3 model calls and 1 lookup. Risk: refunding the wrong order, which the rule caps but cannot detect.
