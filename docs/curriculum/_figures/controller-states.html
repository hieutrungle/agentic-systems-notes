Rows 1–13 · built in the order a run meets them

The controller's nine modes drawn as boxes, with Stopped and Done at the top, Ready to Reconciling down the center, and returns to Ready along the right. The steps below add rows 1 to 13 one at a time.

  1. Start in Ready

    A mode says where the run is. A row says how it may move: in this mode, on this event, if the guard holds, apply the update and go to the next mode. Each step adds one row, in the order a run meets them.

  2. Fired by: Controller rule

    Row 1 · Ready → Proposing

    Event
    Limits checked (controller)
    Guard
    No stop requested, fewer than 5 trials, fewer than 10 proposals, and at least 0.3 GPU-h unreserved
    Update
    Build the policy's context from the ledger

    Ready is the only mode that starts a policy turn, so this check runs before every turn.

  3. Fired by: Controller rule

    Row 2 · Ready → Stopped

    Event
    Limits checked (controller)
    Guard
    A stop was requested or a limit is reached
    Update
    Record the stop reason, freeze the incumbent, and request the holdout score

    Rows 1 and 2 share a mode and an event. Their guards exclude each other, so exactly one fires.

  4. Policy's choice

    Row 3 · Proposing → Authorizing

    Event
    Trial proposed (policy)
    Guard
    The reply answers the current turn
    Update
    Count the proposal and record its arguments

    One of the policy's two choices. A stale reply from an earlier turn fails the guard and matches no row.

  5. Policy's choice

    Row 4 · Proposing → Ready

    Event
    Stop proposed (policy)
    Guard
    The reply answers the current turn
    Update
    Count the proposal and record the stop request

    A stop proposal is a request. Row 2 acts on it in Ready. The policy can ask to stop early, but it cannot keep the run going past a limit.

  6. Fired by: Decoder

    Row 5 · Proposing → Ready

    Event
    Invalid output (decoder)
    Guard
    The report concerns the current turn
    Update
    Count the proposal and record the error for the next context

    A reply the decoder cannot use, or one that misses its deadline, still counts against the 10-proposal cap.

  7. Fired by: Gate

    Row 7 · Authorizing → Dispatching

    Event
    Allowed (gate)
    Guard
    The approval binds the recorded arguments, the estimate fits the unreserved compute, and no stop is requested
    Update
    Mint trial and operation IDs, store the approved request, reserve the estimate, and count the trial. Commit, then send.

    A crash after the commit leaves evidence that the request may have been sent.

  8. Fired by: Gate

    Row 6 · Authorizing → Ready

    Event
    Rejected (gate)
    Guard
    None
    Update
    Record the reason for the next context

    Row 6 comes after row 7 here because a run usually meets an approval first. Nothing was sent. The policy sees the reason on its next turn.

  9. Fired by: Scheduler

    Row 8 · Dispatching → Running

    Event
    Accepted (scheduler)
    Guard
    The operation ID matches the pending trial
    Update
    Record the job ID

    The controller now knows that the scheduler has the job. Completion arrives as a separate event.

  10. Fired by: Scheduler

    Row 9 · Running → Scoring

    Event
    Job done (scheduler)
    Guard
    The job ID matches the pending trial
    Update
    Record the cost and request a score under a scoring ID

    The cost is recorded but not yet charged. The reservation still covers it.

  11. Fired by: Scheduler

    Row 10 · Running → Ready

    Event
    Job failed (scheduler)
    Guard
    The job ID matches the pending trial
    Update
    Charge the cost and close the trial without promotion

    Closing a trial charges its cost, releases its reservation, and moves its ID from the pending slot to the closed set, all in one update.

  12. Fired by: Evaluator

    Row 11 · Scoring → Ready

    Event
    Score (evaluator)
    Guard
    The score is for the pending trial and comes from evaluator v1
    Update
    Charge the cost, keep or discard the candidate, and close the trial

    Promotion happens only here and in row 16. The policy cannot produce a score event, so it cannot promote a candidate.

  13. Fired by: Operator or clock

    Row 12 · Any mode in Search → Stopped

    Event
    Cancel or deadline (operator, clock)
    Guard
    None
    Update
    Record the hard stop, freeze the incumbent, request cancellation of any pending job, and request the holdout score if no trial is pending

    Applies at any moment in the search. The policy cannot prevent it.

  14. Fired by: Fixed evaluator

    Row 13 · Stopped → Done

    Event
    Holdout scored (fixed evaluator)
    Guard
    No trial is pending and no holdout score is recorded
    Update
    Record the final score

    The only edge out of Stopped. The holdout score enters the record only here.

  15. Where the policy chooses

    The policy's reply can fire only the rows leaving Proposing: rows 3 and 4 are its choices, and row 5 records an unusable reply. The gate, scheduler, evaluator, clock, operator, and the controller's own check fire every other row.

  • Blue: the row in the current step
  • Thick line: the policy chooses this edge
  • Dashed line: a hard stop from any mode in Search
