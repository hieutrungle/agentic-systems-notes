Set up once

  1. Fix the protocol Runtime

    Pin the baseline, validation metric, allowed operations, and compute and trial limits. Reserve a separate holdout for final evaluation.

  2. Start the ledger Runtime

    Record the baseline as the initial incumbent, its score, remaining compute, and zero pending jobs. The ledger will track what each trial did and cost.

Repeat one trial at a time

  1. Build context Runtime

    Give the model the goal, relevant ledger entries, latest results, and available operations. On the next turn these inputs reflect the previous trial.

  2. Propose a trial Learned policy

    Choose a configuration that tests a hypothesis, or replicate a promising result. The output is a proposed experiment with arguments such as learning rate and seed.

  3. Authorize Runtime

    Check the arguments, permissions, and compute reservation. Only an approved request can reach the scheduler. A rejected or paused request leaves the job unsubmitted.

  4. Run and score Executor / scorer

    The executor submits the approved request. The scheduler assigns a job ID, workers train the candidate, and the fixed evaluator returns a validation score.

  5. Record result Runtime

    Record the outcome and measured cost, clear the completed job, and promote the candidate if it beats the incumbent and passes the protocol checks. The updated ledger feeds later choices.

  6. Check limits Runtime

    Apply the trial cap, compute limit, and other stop conditions. Continue by building context from the updated ledger, or end the search and freeze the incumbent.

When the search stops

Evaluate the final selection Fixed evaluator

Freeze the selected configuration, then score it on the reserved holdout. The holdout result assesses the frozen selection and stays out of the proposal loop.

What changes between trials? A validation result updates the ledger. If the search continues, the updated ledger can change the next proposal.
